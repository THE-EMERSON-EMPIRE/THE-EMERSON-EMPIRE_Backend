# EPDG phase-two role and permission matrix

This continues the existing intern-built portal, stable core/EPDG identities, custom bcrypt authentication and opaque sessions. It does not authorize a live grant. The eleven canonical roles below are actual server/SQL authorization distinctions, not inferred from an email address, job title, navigation item or legacy profile field.

| Role | Allowed actions and data | Explicit restrictions | Scope |
| --- | --- | --- | --- |
| `founder_owner` — Founder / Owner | Portal account administration, approval of other identities' roles, portal resources, program oversight and publication | Cannot grant to self through the application; no automatic access outside the approved organization; CRM and finance records are not imported into this model | Approved organization |
| `organization_admin` — Organization Administrator | Approved account operations, staff management within the separately approved plan, portal operations/resources and publication | Cannot approve roles, bypass founder approval, manage founder/peer privileged accounts, manage self, or read founder-only resources | Approved organization |
| `hr_admin` — HR Administrator | Education handoff summary and participant progress; approved participant/lead onboarding and account operations | No staff/owner grants, commercial/private client data, publication, or raw CRM applicant/resume/onboarding store | Approved organization, group or explicit resource; account target checks also apply |
| `technical_maintainer` — Technical Maintainer | Assigned technical diagnostics and maintenance content | No automatic HR, participant progress, financial/client access, or account administration | Explicit group/resource |
| `program_coordinator` — Program Coordinator | Assigned curriculum/team drafts, assigned participant progress and review, scoped enrollment/coordination | No organization-wide account administration, role grants or publication; actual learner reviews additionally require the existing mentor mapping | Assigned group/resource |
| `intern_team_lead` — Intern Team Lead | Own participant work plus assigned team/progress review and coordination | No cross-cohort review, enrollment management, publication or organization administration; reviewer mapping remains required | Self plus assigned group/resource |
| `content_editor` — Content Editor | Assigned educational/communications drafts and review; scoped curriculum preparation | Cannot publish or administer accounts; publishing requires a separate authorized operation | Assigned group/resource |
| `sales_staff` — Sales Staff | Assigned commercial materials, drafts and reviews | No outreach/HR/private company access or account administration | Assigned group/resource |
| `global_outreach` — Global Outreach Staff | Assigned institutional/partnership material, drafts and reviews | No commercial/HR/private company access or account administration | Assigned group/resource |
| `restricted_viewer` — Restricted Viewer | Read explicitly permitted individual resources | No organization/group wildcard, edit, review, publish or account administration | Explicit resource only |
| `participant` — Intern / Participant | Own account, own learning/progress/feedback/portfolio/assignment resources, published assigned shared learning/team material | Cannot read another participant's private work, grade/review others, publish, change roles or administer accounts | Self plus approved group/resource |

The first founder scope is an explicit offline bootstrap approved by the founder and executed by the migration operator. The migration does not seed a founder, use an email-based privilege rule, or convert historical `founder_admin` / `webdev_technical` staging records into live authority. Historical role rows remain preserved. A newly approved canonical role is recorded against the same stable user ID.

## Enforcement

`portal_security.role_assignments` remains the role authority. The additive `portal_access.scopes` table attaches organization and group/resource/self scope, founder approver, approval reference, active state and revision. Organization IDs reference existing `epdg.companies`; group IDs are UUIDs in `portal_access.groups`. Group scope grants create a corresponding approved group membership only after the target's approved company membership already exists. Active company and group membership are checked on each decision.

`portal_access.has_permission` evaluates actual active roles/scopes, active account, matching verified core/EPDG mirrors, resource category, resource subject, organization, group and founder-only status. `read_resources` filters rows before returning them. `write_resource`, `review_resource` and `publish_resource` apply the same decision inside the database; edits require the current revision and a draft resource. The runtime receives no direct access to the resource, scope or approval/event tables. Review bodies are separate records; a review does not overwrite a participant's work or silently publish it.

`ScopedAccessService` receives its actor from the existing authenticated session transaction. HTTP bodies cannot choose an approver, user ID, permission, organization, resource status or role through the draft edit operation. Database functions accept the trusted server-derived actor, not a public database user; browser roles receive no EXECUTE. A private SQL credential is a trusted server boundary, never a frontend credential. Provisioning invokes `grant_role` using its persisted, authenticated founder-approved plan; it does not expose a general unapproved role-grant endpoint.

Grant/revoke changes advance the target account revision and revoke its sessions. Scope ID/revision and active membership are included in the session snapshot/fingerprint; membership withdrawal changes that snapshot. The grant transaction takes the already authenticated actor's SHARE lock and the target's UPDATE lock, avoiding an actor lock upgrade behind another request for the same session. Repeating an active grant approved by the same founder retains the original assignment and approval evidence. No operation permits self-grant.

All new tables have RLS enabled and no public privileges. The server role is required to have no SUPERUSER, BYPASSRLS, CREATEROLE or CREATEDB capability. Existing auth/session tables receive explicit policies for this restricted server role, plus only the necessary SELECT, password update, account revision update, session/recovery mutation and audit append privileges. These server policies are not advertised as per-user RLS: private resource rows are enforced by the bounded SQL functions, and learning rows have their own session-bound policies.

## Permission vocabulary

- Own profile: `account.self.read`, `account.self.update`, alias `profile.self.write`; display-only profile edits must never accept authority fields.
- Accounts: `admin.accounts.read`, `admin.accounts.prepare`, `admin.accounts.provision`, `admin.accounts.send` / `admin.invitations.send`, `admin.accounts.disable`, `admin.accounts.audit` / `admin.audit.read`, `onboarding.verify`.
- Privileged approval: `role.grant` / `admin.accounts.approve`, founder only. `admin.accounts.manage_staff` is founder/organization-admin only; provisioning separately blocks peer/founder/HR privileged targets without founder approval.
- Resources: `resource.read`, `resource.edit`, `resource.review`, `resource.publish`, `technical.diagnostics`, `program.coordinate`.
- Existing learning integration: `learning.review` (founder/admin/coordinator/lead), `learning.enroll` (founder/admin/coordinator), `learning.curriculum` (founder/admin/coordinator/content editor), `learning.participate` (participant/lead with explicit group scope). A program maps to `organization_id` and `access_group_id`; existing enrollment ownership, approved HR handoff and mentor mappings remain additional requirements. `learning.curriculum` authorizes draft preparation, never automatic publication.

The session's permission strings are navigation hints. Actual target permissions and returned rows are checked again on each request. A global-looking permission string does not grant organization-wide data access.

## Test evidence

`epdg-backend-core/scripts/local-synthetic/scoped-access-verify.cjs` creates a fresh loopback PostgreSQL cluster on port 55435, a non-superuser migrator, and a separate NOBYPASSRLS runtime; it stops that cluster after verification. It uses only fictional `.invalid` identities and never attaches to an existing database. The latest native run passed **227 checks: 210 access/role checks and 17 account-security regressions**. Coverage includes all eleven roles, positive/negative resource actions, own-profile access with cross-user denial, cross-organization rows, cross-cohort learning verbs, nonfounder and self-grant denial, restricted viewer mutation, content publication denial, stale draft revisions, scope/member withdrawal, runtime identity joins/password policies, direct-write denial, role idempotence, authenticated-session lock ordering, migration replay and transactional failure recovery. Account regressions cover immutable approval, malformed/NULL inputs, exact scopes/organization membership, protected target promotion and sanitized invitation/audit output. Evidence: workspace `build-evidence/epdg-phase2-20261114/scoped-access-native.json`.

Four unit/service tests cover the catalog distinction, default-closed flag, forbidden authority fields in resource bodies, server-derived actor arguments, SQL row-filter usage and migration checksum. The combined phase-two runner separately verifies real bcrypt login/cookie sessions, CSRF, provisioning/invitations and application routes; these SQL matrix results must not be mislabeled as production sign-in proof.

The supplemental `account-lifecycle-checks.cjs` uses actual custom-session/account services and reserved injected mail transports. Its 61 assertions include expired/revoked/rotated/single-use links, failed and uncertain provider outcomes, real session idle/absolute expiry, existing identity/password/history preservation, normalized historical duplicates/mirror conflicts, and concurrent proposal/provision/send/accept/profile operations. Its sanitized evidence binds the applied migration checksums. These checks overlap the combined suite and must not be added together as unique coverage.
